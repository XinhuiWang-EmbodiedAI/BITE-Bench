## 4. 批次 B：建立正式 FoodBench

### B1. 明确食物身份

- 沿用 48 个稳定 food_id，目标为 8 个互斥主类别、每类 6 个。
- 每条明确中文/英文名、品牌或配方、烹饪状态、可食部分、标准份量及描述。生米与熟米饭、同名菜不同配方不可互相替代。
- food_id 不重新分配给另一种食品；需要替换时追加版本/身份变更记录，不静默凑数。
- 先整理明确可检索的食品，再处理复合菜。可先交付一批完整可审记录，但整套不足时不得声称 FoodBench-48 已完成。

### B2. 自动检索与来源保存

- USDA 优先；确有需要时使用可核验官方标签或有许可的数据源。API key 只在本地环境配置，不能出现在日志、页面、导出或 Git。
- 对每条保存查询、匹配候选、选中理由、来源 ID/URL、检索时间、原始响应哈希和来源类型。限流、失败、无匹配如实记录，支持缓存与断点续接。
- 原始数据保存在受控非 Git 目录。当前公开仓库按 AGENTS 要求不提交真实数据；不要因文件在 `data/curated/` 下就默认可公开。
- 需要人工确认的匹配、份量和配方集中到 HUMAN_ACTIONS；机器能补完的字段继续自动处理。

### B3. 标准化与质量控制

字段至少覆盖 FoodVariant 契约：标准份量克数、每 100 g 的 energy/protein/fat/carbs/fiber/sodium、每份蔬果质量、来源及不确定性。关键评分字段按既有 REQUIRED/rubric 校验。

- 明确 kcal/kJ、g/mg、每 100 g/每份；不能把每 100 ml 直接当每 100 g，缺密度或质量依据则保留未知。
- sodium 与 salt 区分；使用转换时保留换算方法和近似说明。零与未知区别处理。
- 缺失维持 null；数据库没给某项不能猜成 0。蔬果含量按可核查构成确定，不能仅凭食品类别推断。
- 多个能量口径、检测限、极值和生熟冲突进入审核；4/4/9 检查只作异常提示，不直接改写源值。
- 配方估算记录所有原料来源、可食质量、烹饪后产出净重、油盐假设、每份分配和计算版本；缺少必要原料营养时向结果传播。标为 recipe_estimate，不升级为标签或实验室测量。
- 图片可暂缺；采用一致的文字展示。若加入图片，保存许可、归属、版本并在采集前冻结展示条件。

### B4. 完成人工审核闭环

现有审核页面只能导出收据。实施者需补齐：**提案修订 → 重新生成卡片/哈希 → 人工决定 → 私有收据导入验证 → 发布审核快照**。

审核卡展示：身份、标准份量、源记录、营养及原单位、换算和配方假设、缺失、风险、证据链接，以及 approve/request_change/reject。字段修改后必须重新审核；不能导入旧哈希批准。

审核收据沿用实际 ReviewReceipt 契约，含 food_id、food_data_sha256、review_status、risk_level、reviewer_id、带时区 reviewed_at、evidence_ref、decision_note、actor_type=human、is_synthetic=false。当前 evidence_ref 校验要求与来源匹配；配方多来源需保留完整证据链，必要的兼容改动要有版本和测试。

导入时验证审核人操作来源、对象和数据哈希、必填字段与冲突；不能相信一段任意 JSON 中的 human 标志就是有效批准。保留追加式私有事件历史，并生成每个 food_id 唯一的当前有效收据视图，兼容当前 ledger 不接受重复 ID 的规则。低风险可批量审核，但每条有独立有效凭据；高风险逐项确认。

### B5. 冻结食品快照

正式快照须列出：食品总数、8 类计数、来源支持数、审核通过数、缺失字段、来源类型组成、可用于评分数、被排除项及原因。每个数据文件有 SHA256、schema/转换版本和代码版本，收据绑定规范化食品记录哈希。

验收：

- [ ] 每个纳入食品的身份、份量、来源和必要营养可核查，审核有效。
- [ ] 自动检查不伪装成人工批准，关键字段变更使批准失效。
- [ ] 单位、空值、配方与来源回放测试通过。
- [ ] 报告目标 48 与实际通过数量；不足则正式完整数据集 BLOCKED，不能用 synthetic 补齐。
- [ ] 冻结快照后按版本引用，不在采集过程中自动覆盖数据。

## 5. 批次 C：建立日菜单

1. 从审核有效的食品组合 60 份候选完整日菜单，明确 breakfast/lunch/dinner、food_id、servings、profile 和采样理由；禁止原料与成菜重复计算。
2. 由现有确定性营养引擎计算每份、每餐、每日总量；完整 Oracle 规则未实现的部分按原 Phase 5 公式补齐并验证，不用 LLM 填数。
3. 依既有约束区分 reference_valid、stress_case、insufficient_data。压力案例保留真实违规状态，不伪装成合法候选；模拟的合法候选过滤与问卷展示资格分别定义。
4. 检查份量、三餐结构和整体可读性。研究负责人确认异常菜单和估算说明；保留菜单审计与食品快照引用。
5. 正式问卷不使用关键数据缺失的菜单；有意采用营养偏离的压力案例时，在协议中明确其问卷用途与分析范围。
6. 冻结 development 与 final evaluation 的菜单/比较对安排，保证用于开发的菜单不进入最终菜单测试。现有 synthetic 的 36/24 划分仅为夹具；正式划分数量、覆盖和配对方案由预注册方案确定，不能直接复制后当作方法既定值。

验收：60 份目标菜单均有审计记录，实际可评分/可问卷/合法候选数量分别报告；来源变化能使依赖菜单及题库的版本校验失效；不能用不合格菜单凑满正式测试。

## 6. 批次 D：统一采集应用与研究后端

### D1. 接入架构

建议保留现有浏览器界面，以根项目研究服务为统一业务实现；浏览器和 CLI 都调用同一套会话、采样、冻结与导出服务。

```text
审核食品快照 + 日菜单快照 + 收据验证
                    ↓
版本化题库适配器 + protocol/split 锁 + 同意文本版本
                    ↓
统一研究服务（阶段控制、采样、随机化、校验、私有存储）
          ↙                              ↘
浏览器 BITE Collect                    研究 CLI
                    ↓
train / ratings / sealed test / menu development / sealed menu test
                    ↓
TasteNet、开发与最终评价各自只读取获准分区
```

不要继续复制两套研究规则。统一存储须选择一个当前写入源，另一个旧库只读保留；不可将历史合成库迁成真人库。任何迁移先备份、版本化验证和测试，不能直接覆盖。

根项目依赖 NumPy/SciPy/Pydantic，现有浏览器离线包主要为标准库程序。接入主动学习后必须重新构建兼容 Windows 的锁定运行时与依赖，不得假定旧 ZIP 能直接运行新后端。首次集成可在已验证 Python 环境运行，再交付重新验收的便携包。

### D2. 统一题库与研究配置

适配器读取已审核快照，不手抄食品。展示对象包含 food_id、名称、变体、标准份量、描述及已授权图片；菜单对象包含三餐和可重算营养。额外元数据建议放侧表/版本化清单，避免破坏原有必填契约。

必须绑定：study_id、study_level（pilot_dev/pilot_eval/full_study）、mode、schema_version、food/menu snapshot hash、review snapshot hash、protocol/split hash、consent version/hash、questionnaire version/hash、代码版本。清单不携带私人同意记录或测试答案。

test pair、heldout food、训练锚点、固定覆盖题、训练候选池、策略参数和分组规则在任何回答前冻结。主动查询的后 20 个实际题目不能预先固定为单一序列：冻结的是候选池和选择算法，运行中逐次保存实际选题与模型状态。

已有冻结文件只读，新研究生成新版本。正式模式不能复用 syn_* ID 或 synthetic 回答。

### D3. 服务接口和职责（拟实现契约，不是已有 URL/命令）

| 操作 | 服务端必须保证 |
|---|---|
| 创建会话 | 启动门禁通过、版本化知情同意确认、匿名 ID、研究层级、分组及冻结引用在首次回答前落盘 |
| 下一题 | 只返回当前允许展示的题；已分配未回答题稳定重放；不向前端暴露测试答案、未来题序或纯美味阶段的隐藏营养 |
| 提交答案 | 验证题目确属本会话、展示顺序、阶段和合法值；事务提交后才确认；同 payload 幂等、不同 payload 冲突 |
| 暂停与恢复 | 使用私有 token 校验，恢复数据库已确认状态；服务重启/刷新不会重抽题或双计 |

| 菜单题 | 隐藏/显示营养阶段由服务端控制；第二阶段来自冻结引擎结果；保留同一 pair 的实际左右顺序 |
| 进度 | 区分题目、回答、跳过、完成和有效样本；采集员默认只见进度，不见最终测试选择 |
| 导出 | 训练白名单与封存测试分区；权限和用途校验、实际计数、哈希、不可覆盖；不能默认一次导出所有答案供训练 |
| 撤回 | token 验证、库内关联数据处理、已导出/备份影响清单及处理记录；不得只删当前库就声称所有副本已删 |

MVP 为受控电脑上的 localhost 浏览器采集，优先继续离线方式。多人分批使用同一设备即可，不需要开放 5060 公网端口。远程在线招募、跨设备同步和集中服务器是独立部署任务，不在本轮默认范围。

### D4. 问卷状态机

**H1：** 说明/成年/自愿确认 → 匿名 ID 与恢复码 → 20 道固定覆盖训练题 → 20 道 active 或 random 训练题 → 10 道冻结测试题（5 known、5 cold）→ 8 个训练锚点 0–10 评分 → 完成/暂停。

纯美味题只问“预期好吃程度”，不显示营养、模型分数或系统建议。是否吃过与饥饿程度自愿填写，左右位置随机化并记录。tie/skip 原样保留；二分类训练按预注册规则排除或建模，不能改为随机标签。

active 使用训练数据的 p*(1-p) 等已冻结策略；保存候选池、训练数据和模型状态哈希。现有 synthetic query model 不是正式 TasteNet，必须完成真人数据兼容、隔离与策略版本验证后才能使用。候选池不含 heldout food 或测试 pair，也不使用其他会话的最终测试答案。

**H2：** 方法冻结且门禁开启 → 固定说明 → 12 个菜单 pair 隐藏营养选择 → 同 12 个 pair 显示营养后选择 → 完成/暂停。先完成整个隐藏阶段可沿用当前实现；如采用其他展示安排，须在采集前明确冻结。不得显示 M0–M4 的推荐或分数来诱导答案。

H1 完成后，H2 只有满足独立评价条件才开放；不能为了“一次问完”提前拿最终菜单答案调 Prompt。开发菜单问卷必须有单独 study_level 和 development 分区。

### D5. 正式模式启动门禁

启动检查至少验证：食品/菜单资格、收据与快照 hash、研究协议及划分、题库一致性、版本化同意文本、机构审批/豁免或适用性确认记录、用户明确启动相应采集的记录、正确的私有存储位置和可用备份/撤回流程。

`collect_real_human_responses=true` 本身不构成许可；只改变 JSON 标志、路径或模式名也不能通过。任一条件不满足返回 BLOCKED 和具体 reason_code。H1 与最终 H2 分设启动条件，允许在 H2 尚未准备时合法完成 H1。

| 正式输入混入 synthetic、缺审核或收据 hash 不符 | 拒绝正式启用 |
| 必要营养缺失、份量/单位不合法 | 生成明确原因；正式评分和相关菜单被阻断 |
| 全流程合成规模 | 24 合成会话、12 active/12 random；每人 40 train + 10 test + 8 ratings + 12 菜单 pair 双阶段 |
| 合成规模计数 | 无跳过的自动夹具应有 train 960、test 240、ratings 192、菜单阶段记录 576；288 是参与者×pair 观测，不是 288 个参与者，亦不一定是 288 个全局不同 pair |
| 浏览器与 CLI 同一已锁定状态 | 阶段、题目和导出语义一致；界面差异不改变研究逻辑 |
| 主动学习/模型调参尝试访问测试分区 | 服务/API 和训练输入校验拒绝；不靠前端隐藏 |
| 对称 pair、冷食物和锚点 | 训练/测试不重叠；冷食物不参与训练、词表拟合或锚点校准 |
| 刷新、双击、重试、并发提交、重启 | 同答案只计一次；未确认 payload 不假称已保存；恢复不重抽题 |
| 左右互换与 skip/tie/零评分 | 选择语义正确；缺失不改零；0 分可明确提交 |
| 菜单第一阶段检查网络响应/页面 | 无隐藏营养字段泄露；显示阶段与同一冻结菜单一致 |
| 篡改快照/已有冻结文件 | 读取、提交或导出明确失败，不能自动重算 hash 掩盖变化 |
| 撤回与备份恢复 | 当前记录及衍生数据影响可追踪；恢复备份不会静默复活已撤回者 |
| 导出训练、最终测试、开发菜单 | 分区明确，训练默认不含最终答案；包中没有同意原件、token 或密钥 |
| 换人和权限 | 看不到上一人的码和答案；采集员无代答/改写入口 |
| Windows 发布包 | 在目标 Windows 原生运行；浏览器完成至少一遍流程、暂停恢复、导出与撤回；记录实测环境 |

未来应用交付必须包含原生 Windows 浏览器验收，不能用 WSL 的 Python 测试替代。用合成会话做故障测试；未达到正式门槛时不调用真人来替软件做测试。

## 8. 批次 E：真人采集准备与开发性试点

### E1. 研究负责人需确认的事项

由工程方准备完整可审材料后集中交付，不要求负责人手填营养表：

1. 食品审核批次、特殊配方假设及菜单异常。
2. 采用 hybrid_pilot 还是扩大到 full_study；保持正式目标 24 位成人、48 食品和 60 菜单，不能把小试点写成完成目标。
3. 按学校要求取得适用的伦理审批、豁免或程序确认，再邀请他人。
4. 同意文本具体写明用途、保存期限、访问者、撤回方式和截止规则、公开范围；这些必须是真实安排，不能保留占位符就启动。
5. 确认本地采集地点/设备、数据负责人、采集员和私有备份位置；联系方式如因组织需要产生，另行保管，不进入答案表。

### E2. 开发性试点

建议获准后先由用户本人或少量自愿成人做 pilot_dev；具体人数是可行性安排，不更改 full_study 的 24 人目标。试填数据若被用于查问题、改文案、选算法或调权重，必须始终保留 pilot_dev 标签，不能后来改成最终评估数据。

先完整走一次流程，实测题目理解、份量可读性、跳过率、暂停恢复和完成时间。页面显示的耗时须区分含暂停的 elapsed time 与有效作答时间；当前实现计时包含暂停，不据此自动剔除“异常慢”参与者。

在此阶段制定并冻结缺失/退出/重复参与/不完整会话处理规则、tie/skip 规则、有效样本定义和质量标记。不能在看到正式结果后再决定剔除标准。存在重大问题时修复并新建版本再测，不静默修补旧会话。

交付：试点报告、实测时长、问题与修复清单、最终文案、启动检查结果。正式采集时间表此后按实测时长制定，不预先承诺每人固定分钟数。

## 9. 批次 F：正式 H1 美味偏好采集

### F1. 首位参与者作答前

- 冻结真实食品快照、协议、全局 heldout food、每人 10 道测试题及左右安排规则、8 个训练锚点、20 固定覆盖题、20 次查询预算、分组和缺失处理规则。
- full_study 目标 24 位成人，active/random 目标各 12。分配事先随机化、可审计；退出和不足按预设规则报告，不能根据偏好结果换组或补人。
- known-food 测试食品确实在训练覆盖中出现，cold-food 全局不进入训练/校准。heldout 数量可按原方案例示 8 个预注册；不能把合成夹具的按 ID 排序选取当成正式抽样依据。
- 训练 query model 的算法、超参数和选题规则先冻结。在线用已取得的 train 答案更新参数属于预定算法；不能在线查看 test 表现选择策略。
- 最终测试答案单独封存；后续 TasteNet 超参数通过 train 内部验证选择。若观察 10/20/30/40 预算曲线，保存每个预算训练状态，待方法锁定后统一在封存 test 上评估，不拿中途测试曲线反复选模型。

### F2. 每位参与者的操作

1. 采集员核对设备/版本和空白会话；读统一说明，不介绍哪种食物“应该”更好。
2. 参与者确认知情、自愿、成年；创建匿名 ID，私下保存恢复/撤回码。
3. 按状态机完成 40 次训练选择、10 次测试选择、8 个锚点评分；允许跳过、暂停，不要求为了完整率强行作答。
4. 完成后只显示个人进度和恢复/撤回方式，不给出测试“答案”或模型对错反馈。
5. 采集员做技术完成确认，记录中断原因，不查看或更改其偏好。每日检查完整性并私有备份。

24 人全部完成时的计划量：960 条训练比较、240 条测试比较、192 个锚点评分。实际有效二分类样本可能因 tie/skip/撤回更少，分开报告；这是目标计数，不是现有结果。

## 10. 批次 G/H：方法开发、冻结与独立菜单采集

这是避免“数据收齐了却不能用于正式评估”的关键顺序。

1. **开发集先行**：用合法 train 数据训练/校准 TasteNet；实现并验收 Phase 5–7。需要调 Prompt、权重或拟合菜单选择概率的 κ 时，使用单独的 development 菜单选择资料。
2. **补足开发菜单资料**：在 pilot_dev 阶段单独安排 development 菜单问卷或专门开发批次，预先记录人数、pair 和负担；不能从每人 12 个最终菜单测试 pair 中临时抽答案调 κ。若没有合法开发标签，κ 校准及相应正式概率指标继续 BLOCKED，不自造标签或暗改为任意参数。
3. **区分参与者与数据独立性**：同一人可以提供 H1 训练偏好并参与 H2，这是个性化设计的一部分；其 H2 最终答案不允许开发使用。参加 pilot_dev 的人若再次进入最终研究，使用新冻结且未被开发使用的评价资料，并在协议中说明；复用同一测试答案不成立。
4. **锁定全部比较方法**：模型/校准/Prompt/rubric、M0–M4、LLM digest、预算、最终菜单和 pair、统计计划全部生成锁定记录。最终 H1 测试也只在相应 TasteNet 方法选择结束后开启评价。
5. **开启最终 H2**：对目标参与者收集每人 12 个冻结日菜单 pair 的两阶段选择。先隐藏营养，后显示规范化真实营养与必要估算说明。两阶段不显示 Agent 输出。
6. **封存与评价**：H2 的 overall_visible_nutrition 为主要效标；taste_hidden_nutrition 用于预先声明的探索性分析。final 标签不回流给 Prompt、训练或选择模型。

24 人完整 H2 的计划量是 **288 个参与者×菜单 pair 观测、576 条阶段回答**。分别报告参与者数、全局唯一 pair 数、完成双阶段 pair 数和有效记录数；不能把 576 当作独立比较数。

H1 与 H2 可以分两次会面完成。仅在上述全部方法冻结已经满足时才可连续安排，不能因现场方便省掉开发与独立评价之间的边界。

## 11. 私有数据管理、质量控制与交付分析

- raw responses 作为原始事实保存。需要更正时追加事件，保留原回答和更正理由；不直接改写原记录。
- 建议按 `synthetic/`、`pilot_dev/`、`pilot_eval/`、`full_study/` 分开数据库/目录，并保留来源字段；真实数据放 `data/private/` 或等效受控位置，导出、备份、同意和审计同样私有。
- 为每次导出记录 export_id、study/version、源库快照、实际行数、文件 hash、访问用途和生成时间。跨采集设备时使用 UUID 和事件 ID 去重，并以相同协议/快照 hash 校验兼容性；不直接拼接冲突 CSV。
- 备份用 SQLite 一致性备份接口；验证可恢复。建立私有撤回清单，列出受影响的导出、备份和衍生模型，按已声明规则删除/重建并防止恢复后重新纳入。
- 正式采集中发现问题：暂停受影响模块，保留失败与受影响会话；数据层如实标记。需要改协议则建立新版本，旧数据的可用范围另行记录，不拼成“同一版本”的主实验。
- 质量报告计算 consent 完成数、参与者/会话数、各组数量、train/test/anchor 有效数、tie/skip、退出、撤回、菜单双阶段配对和版本一致性。浏览器会话数不自动等同独立参与者人数。
- 单人/少人 pilot 作为个人案例，不把题目当成人群独立样本生成群体 CI。full_study 按参与者聚类 Bootstrap，实际人数不足要披露。
- 后续 Phase 9 的 7/30 天结果明确为模拟；Phase 10 所有图读取真实 metrics 和 manifest；Phase 11 交付实际完成/未完成、重跑命令和资源日志。
